# 不具合と性能低下の診断

症状に関係する証拠を集め、確認済みの原因と仮説を区別する。診断のみの依頼を設定変更へ広げない。

## 最初に確かめること

- 対象のアプリ、症状、起こる操作、実行環境を既存の会話・設定・ログから特定する。不明な症状が診断を左右する場合だけ質問する。
- ホスト、コンテナ、仮想環境、Flatpak の違いを確認する。対象が見えない環境の観測は、その対象に不具合がある証拠にはならない。
- 既存のログ、設定、関連コードを読み、最小の確認方法を選ぶ。再現テストを作る前でも、原因を調べるためのコード確認は進めてよい。
- 認証情報や個人情報は出力に含めない。診断に必要な行だけを扱う。

## 原因を絞り込む

- 再現できる場合は、ユーザーの症状を検出できるコマンドやテストを使う。既存のテストや実行経路を優先する。
- 性能問題では、まず時間、CPU、メモリ、フレームレートなど症状に対応する値を測る。条件を揃えて比較する。
- 証拠から有力な仮説を立て、それぞれを区別できる確認を行う。仮説数や再試行回数を固定しない。
- 手元で再現できない場合も、ログや静的な確認は進める。何が未観測かを説明し、結論に必要な最小の追加情報を求める。
- 画面の色・レイアウトや機器の入力は、その画面・機器で確認する。ヘッドレスの成功だけで表示や実機の問題が解決したと判断しない。

## 修正を求められた場合

- 変更する処理の呼び出し元と関連経路を確認し、原因がある箇所を直す。正常な設定を推測で置き換えない。
- 元の症状を再確認する。挙動の変更を守る必要がある場合は、実際の不具合を検出する小さな回帰テストを残す。テスト先行が指定されたらその順序を守る。
- 関係する検証が通り、残る懸念がなければ終了する。調査用の一時変更は自分の分だけ整理する。
- 原因、変更、実行環境、観測結果、未確認の範囲を報告する。

人の操作が必要な反復確認には、必要に応じて [操作記録用のテンプレート](scripts/hitl-loop.template.sh) を使う。
