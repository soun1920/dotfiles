# Clef で判断する

Clef は文章を生成せず、渡した選択肢それぞれの確率と確信度(confidence)を返す。
選択肢の外の答えは返らない。LLM より安く速いので、件数が多い分類に向く。
モデル ID は `@cf/cloudflare/clef-flash`(9B、速い)と `@cf/cloudflare/clef`(27B、精度重視)。
まず flash で試し、確信度が低い対象だけ `clef` で再判定する。

## 手順

1. 前提を確認する。`cf auth whoami` で `authenticated: true` なら API トークンは不要。未ログインなら、ユーザーに `! cf auth login` を頼む。
2. 質問を決める。型は 3 つ。

   | type | 内容 | 選択肢 |
   |---|---|---|
   | `choice` | 候補から 1 つ | 2〜255 個。`criteria` に {名前: 説明} |
   | `noul` | はい/いいえの確率 | なし |
   | `score` | 順序のある段階 | 2〜10 段階 |

3. リクエストを JSON ファイルに書き、`cf ai run` で呼ぶ。

   ```json
   {"model": "clef-flash",
    "state": {"filename": "信号処理 第3回.pdf", "content": "フーリエ変換 …"},
    "questions": {"category": {"type": "choice", "instructions": "どの授業か。",
      "criteria": {"信号処理概論": "FFT・フーリエ変換・フィルタの授業", "other": null}}}}
   ```

   ```bash
   cf ai run @cf/cloudflare/clef-flash --body @req.json
   ```

   `state` は文字列でも JSON でもよい。画像は 1 リクエスト 4 枚まで(各 4 MiB)。全体で 65,536 トークンまで。
4. 応答は stdout の JSON。`answers.<質問名>.choice`、`probabilities`(全選択肢)、`confidence` が入る。`usage.output_tokens` は常に 0 で、課金されない。

## 最新のドキュメントを読む

API の細部(制限、料金、モデル)は変わる。実装の前に最新の資料を読む。

- Clef 本体: <https://developers.cloudflare.com/workers-ai/models/clef/>
- 設計の考え方: TypeSafe の公式スキル(<https://raw.githubusercontent.com/typesafe-ai/skills/main/skills/typesafe-ai/SKILL.md>)と、そこから辿れる <https://docs.typesafe.ai/llms.txt>。
  Clef は Jev と API 互換とされているので、質問の書き方や確信度の扱いは Jev 側の資料が参考になる。互換の範囲は、実際に呼んで確かめる。
- 読めないときは、分からない箇所を推測で書かず、そう伝える。

## 質問の設計(TypeSafe の公式スキルより)

- 1 つの質問では、1 つの狭い判断だけを聞く。独立した観点は質問を分ける。
- **同じ `state` に対する独立した質問は、1 回のリクエストにまとめる。** 並列に処理され、互いの答えは見えない。前の答えが次の入力に必要な場合だけ、リクエストを分ける。
- 質問 ID(`questions` のキー)はモデルに送られない。意味は `instructions` と `criteria` に書き切る。
- `state` は、複数の部分があれば名前付きの JSON にし、`instructions` では `` `ticket.text` `` のようにパスで参照できる。
- 複数のラベルが同時に当てはまりうるときは、`choice` ではなく、ラベルごとに `noul` を 1 つずつ置く。
- 候補を選ばせる場合、正解が候補に含まれていないと選べない。候補の漏れを先に確認する。
- コードで確定できること(拡張子、完全一致、計算)は Clef に聞かない。意味の理解が要る判断だけを任せる。
- 確信度は選択肢の確率の集中度であり、ワークフロー全体の正しさではない。閾値は自分のデータで決める。`noul` が 0.5 付近なのは「中程度」ではなく、「はい」と「いいえ」が拮抗している状態。

## プロンプトの書き方(実測で分かったこと)

- **各選択肢の説明に、中身を表す語を入れる。** 科目名と担当者名だけの説明では、本文の主題と照合できない。英語の授業なら「英語で行う」と書く。
- **「どれにも当てはまらない」ための選択肢を必ず置く。** `null` の選択肢は名前だけで判断される。説明が薄い受け皿は、何でも吸い込む。
- **確信度が高くても正しいとは限らない。** 該当なしの文書が、近い名前の選択肢に 0.88 で入った例がある。確信度は「選択肢の中での相対」であって、正誤ではない。
- 指示には「ファイル名より本文を重視する」と書く。
- 検証では、試す対象の答えになる語を説明に入れない。入れると結果が良く見えるだけになる。

## 結果の扱い

1. `choice` が `other` なら何もしない。
2. `confidence` が閾値(最初は 0.7)未満なら、動かさず人に回す。
3. 破壊的な操作(移動・削除・送信)は、先に「対象 → 判断 → 確信度」の一覧を作ってユーザーに見せ、承認された分だけ実行する。dry-run を既定にする。
4. 失敗した対象(`cf` の非 0 終了、JSON が読めない)は、元の場所のまま残し、一覧に失敗として載せる。1 件の失敗でバッチを止めない。

## 外に出る情報と費用

- `state` に入れた文字列と画像は、そのまま Cloudflare に送られる。パスワード、鍵、個人情報が含まれそうなものは送らない。ファイルなら先頭 100 行程度に切る。
- 料金は入力 100 万トークンあたり 0.24 ドル。先頭 100 行(約 1,000〜3,000 トークン)で 175 件を判定しても数セント。

## 手元で確認できる範囲

`cf ai run @cf/cloudflare/clef-flash --help` で入力の形式を、`cf ai get-model-schema` でスキーマを確認できる。
`cf` が使えない環境では、REST でも呼べる。`POST /client/v4/accounts/$ID/ai/run/@cf/cloudflare/clef-flash`、`Authorization: Bearer $TOKEN`。応答は `result` の下に入る。
