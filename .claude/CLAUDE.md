ponytailのようなローカルツール限定の見出しは使わず、誰でもわかる言い回しにすること

## 作業の進め方

- 環境を決めてから結論を出す。ホスト（Fedora、Nix と mise）、distrobox コンテナ（ros2-humble、ros2-jazzy）、Flatpak、venv のどれで動くものかを先に確かめ、「無い」と結論する前に該当する環境の中で調べる。結果を報告するときは、どの環境で実行したかを書く。
- 設定ファイル（niri の config.kdl、DankMaterialShell、fcitx5、xdg-desktop-portal など）を編集したら、そのツール自身の検証コマンドで確かめてから完了と言う。キー名や ID の表記（snake_case か camelCase か）は、インストール済みのバージョンの実物で確かめる。
- 既存の記事や文書を手本にスキル、文体規範、チュートリアルを作るときは、書く前に実物の出典を 10 本以上読む。推測で書き始めない。
- sudo、対話入力、実機や GUI の操作が必要な手順は実行せず、番号付きの手順書（コマンド、期待する出力、違ったときの対処）にして渡す。
- 日本語の文章は段落で書き、比喩的な動詞（捕まえる、黙って捨てる、効く）や地の文のダッシュを使わない。技術原稿は `~/.agents/skills/japanese-tech-writing/` の手本と規範に従う。
- 原稿の推敲は 3 ファイルずつ進め、そのたびにビルド（mkdocs build --strict、typst compile）を通す。同じディレクトリを別のセッションが編集していないか、始める前に git status で確かめる。
